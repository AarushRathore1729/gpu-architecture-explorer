Precision-specific compute ceilings

Compute ceilings come from dedicated calibration GEMMs. Each precision gets its own ceiling.
Arithmetic intensity assumes ideal operand reuse and one output write. It does not measure off-chip traffic. TF32 results use float32 buffers with an explicitly enabled TF32 mode.

How to read the roofline

Sloping region

The logical-byte bandwidth estimate constrains performance as arithmetic intensity rises.

Flat region

The measured calibration GEMM throughput supplies a precision-specific compute ceiling.

Gap to the line

Small shapes, insufficient parallelism, launch floors, and reuse assumptions can create a gap. These are hypotheses to inspect, not hardware-counter diagnoses.

Useful-byte throughput

Contiguous copy and AXPY by working-set size. Copy counts read + write; AXPY counts two reads + write.

Access-stride sweep

Each line keeps the Triton block size fixed. The input address span grows with stride.
Effective GB/s counts useful values, not fetched memory transactions. Repeated buffers can hit L2. Triton uses .cg loads; the suite does not flush L2 or report physical HBM bandwidth.

A transparent runtime estimate

t̂ = max(F / P, B / W, launches × t_floor)

F is useful FLOPs, B is minimum logical bytes, P is the matching precision's empirical compute throughput, and W is the large-buffer copy calibration.

Calibrate

Large square GEMMs, a streaming copy, and a one-element fill set the model parameters.

Evaluate

Different GEMM shapes, memory sizes, and reductions are excluded from calibration and used for error summaries.

Inspect limitations

Cache residency, implementation differences, and reduction stages limit a simple roofline estimate. Strided copies are excluded from scoring.
